# 公告

> 狀態：0.5.22 程式碼｜平台：Android、iOS（差異見「平台差異」）｜2026-10-13 候選核對；2026-10-14 改版候選 (尚未發布)；2026-10-17 青少/主堂分頁、主堂週刊；2026-10-19 週刊圖片在 Android 也帶登入 token；2026-10-20 週刊只收公布欄群組、週刊載入中的灰框、清單用手機大小的圖、放大畫面不蓋狀態列

## 一句話

公告分頁顯示下次聚會的資訊、每個主日的講道紀錄、報名狀況與常設資訊；資料直接讀公開發布的 JSON，就算後端伺服器沒開機也能看。

## 從哪裡進

- 登入後，分頁列最左邊的「公告」（喇叭圖示），對應 `app/(tabs)/announcements.tsx`。
- 這個分頁本身讀的是公開 JSON、不用登入也能讀，但**整個 App（含公告分頁）在 Expo Router 的層級就先卡了登入**：`src/ui/AppStack.tsx` 用 `Stack.Protected guard={signedIn}` 把 `(tabs)` 整組（公告在內）鎖住，沒有登入或登入過期的人會先看到 `app/sign-in.tsx`（見 [account.md](account.md)）。

## 功能一覽

| 功能 | 使用者看到什麼 |
|---|---|
| 下次聚會 | 左邊深色日期塊 (10 月 / 18 / 週日)，右邊主題 (或兩堂各自的信息/內容)；下面服事名單、報名按鈕與報名人數 |
| 青少｜主堂 | 最上面兩個分頁，預設打開自己那一邊 (歸屬見 [account.md](account.md))，兩邊都可以點 |
| 主堂週刊 | 主堂分頁只放週刊：最新的主日在最上面，每週幾張照貼出的順序排，保留 8 週；點一張全螢幕放大 |
| 講道紀錄 | 一個主日一張卡，最新的在上、標「上週」；卡片左邊是日期，右邊每堂的名稱、講員、經文與資料連結；沒有內容的堂次收成一行 |
| 常設資訊 | 教會提供的固定資訊（例如地址），網址自動變成可點的連結 |
| 版本更新卡片 | 分頁最上方，手機版本落後時常駐顯示（見 [account.md](account.md)） |
| 離線/過期提示 | 抓不到最新公告時，安靜顯示「目前顯示是哪一週」的小字 |

## 行為規格

### 資料來源與快取（`src/services/announcementClient.ts`）

- App 開啟或切回這個分頁時都會重新抓一次：`app/(tabs)/announcements.tsx` 用 `useFocusEffect(load)`；公告本身**沒有其他輪詢**，因為一週最多改兩次。
- 一進分頁會先顯示裝置上「上一次成功抓到」的快取（`readCached`），同時背景重新抓最新的；等最新的抓完才用它蓋掉畫面，避免畫面先空白再跳動。
- 抓取網址固定是 `https://raw.githubusercontent.com/oxydavid-maxx/spllt-bible/main/announcements/latest.json`，8 秒逾時。
- 抓取失敗（逾時、HTTP 非 2xx、JSON 壞掉、或內容解析不出必要欄位如 `week`）時：畫面**不會**顯示錯誤或空白，而是顯示裝置上的舊快取並標記為「過期」；如果裝置上也沒有任何快取，公告卡片全部不顯示，只留一行「還沒有本週公告。」。
- 只有解析成功的內容才會覆蓋裝置快取，避免一次壞的發布把舊的好內容也毀掉。
- 解析採「只認我知道的欄位，多出來的欄位忽略、缺欄位的區塊整塊不畫」策略，所以舊版 App 讀到新版多加的欄位不會壞，新版 App 讀到舊格式的檔案也不會空白一片。

### 下次聚會卡片（`src/ui/AnnouncementBoard.tsx`）

- 卡片最上面「下次聚會」，左邊一塊深色日期：上面「10 月」、中間大字「18」、下面「週日」(`nextDateBlock`，`src/ui/announcementModel.ts`；星期由公告的週次推算，日期寫法認不出時只顯示原文)。
- 有 `next.sessions`（兩堂內容不同）時，畫兩個堂次各自的標籤、主題與負責人；沒有 `sessions` 時退回單一 `topic`/`owner` 那一行。
- 發布檔案怎麼填這幾個欄位（`tools/announce/build.ts`）：
  - 第一堂：從「中亮第一三周信息排班」（類別「信息」）或「中亮第二四周青年啟發內容」（類別「青年啟發」）那一週的列，標題取主題格的第一行，負責人照抄。
  - 第二堂：「正慧姐青崇一三周第二堂規劃」或「小丁第二四周第二堂」那一週有規劃列時才有，標題取主題格的第一行，負責人照抄，沒有類別，例如「第二堂 吃喝玩樂躺平系列: 青年館電影院」，下面一行是負責人；Note 欄 (例如連假) 不寫進發布檔案。那一週兩個分頁都沒有規劃列時，不顯示第二堂。
  - `topic`/`owner`（舊版 App 只讀這兩個）：第一堂的標題和講員；那一週只有第二堂時，是第二堂的標題和負責人。
- 有 `next.roles`（服事名單，例如講員、主領、招待）時，在卡片下方另起一段 grid 顯示每個角色與對應的人名，欄名照發布檔案給的名稱，但括號和「+」後面的備註不顯示 (「主領(報告)」顯示「主領」，`shortRole`)；報讀螢幕的人仍聽到完整名稱。不是寫死的固定清單。
- 有 `next.signup`（報名連結）才會出現「報名」按鈕，按下用 Chrome 分頁開啟外部表單。
- 報名狀況（已有幾人報名/朋友是誰）只在「已登入」且「能把公告上的日期換算成日曆日期」且「伺服器有回應」三個條件都成立時顯示；任一條件不成立就只是不顯示這一段，不會出現錯誤訊息（`app/(tabs)/announcements.tsx`）。
- 報名人數為 0 時完全不顯示報名狀況區塊（即使已登入且日期换算成功），因為 `registration.total > 0` 是顯示的前提。

### 講道紀錄 (`src/ui/announcementModel.ts` 的 `sermonWeeks`)

- 2026-10-14 起「上次講道」和「以前的主日」合成一段「講道紀錄」：一個主日一張卡，最新的在上；公告本身那一週 (上週) 的卡標「上週」，其他週不標。
- 每張卡左邊是日期 (今年 `9/20`、其他年份 `2025/12/13`)，右邊一堂一段：多堂時有「第一堂/第二堂」標籤，接著名稱、「講員 · 經文」、資料連結。
- 資料連結是文字加小圖示 (錄音、投影片、文件、影片)，依「錄音、講道投影片、報告投影片、逐字稿、教材」排序，最後是影片；同一類有兩份以上時編號「報告投影片 1、報告投影片 2」，不顯示檔名。
- 一堂沒有講員和經文、資料不超過一份時 (常見是第二堂)，收成一行：標籤、名稱，有資料就放在行尾。
- 以下是資料來源與發布工具的規則 (2026-10-13)。


- 新公告加上頂層 `sessions`，歷史各週也可帶 `sessions`。每堂有 `label`、`title`、`speaker`、`passage` 與資料；新版 App 優先讀它，沒有時照舊讀 `sermon`/`past`。
- `sermon` 及 `past` 的既有欄位仍代表第一堂，沒有第二堂資料混入；舊 App 忽略新增欄位後照常顯示第一堂。
- 多堂時在那一週的卡片內各自顯示第一堂/第二堂標籤、名稱、講員與資料連結；單堂不加堂次標籤。沒有講員或某種資料時不顯示該行/連結。
- 每堂的 `materials` 保存多份同角色檔案，不會只保留第一份。同角色超過一份時，App 編號顯示 (「講道投影片 1、2」)；第一份也投影到既有連結欄位供舊版 App 使用。講稿/小組文件以「教材」顯示，不誤稱逐字稿，舊欄位不受影響。
- 公告工具匿名讀取檔名、投影片文字、文件開頭及當週同一份分堂服事表，以一週一批的便宜級 LLM 分類，分為報告投影片、該堂教學投影片、錄音、逐字稿及其他資料。PPTX/Google Slides、DOCX/Google Docs、文字檔直接擷取；PDF 用可取得的 `pdftotext` 讀前三頁，工具缺少或內容讀不到時保留 unknown。錄音不做付費轉錄。
- 判斷讀不出、呼叫失敗或回應不合法時，退回原本檔名規則並逐檔記錄 `CLASSIFY FALLBACK <檔名>`，分類失敗本身不擋發布。原有必需來源、連結及結構檢查照常適用。
- LLM 只決定堂次/角色；顯示用的公開標題/講員必須出現在檔案內容中，否則保留服事表的名稱/講員。第二堂的名稱來自規劃列的主題 (見上面「下次聚會」)，規劃列也交給分類參考。
- 分類 model/effort 從 `skill-brain dispatch plan` 的便宜查找級取得，沿用專案受限且無工具的 Claude CLI；不寫死 model 名稱。分類快取綁內容、服事表、prompt、model/effort，所擷取內容或檔案清單變動時重判。沒有常駐程序。
- 「以前的主日」來源只保留有效週日資料夾，而且在所選週日向前八個週距內；缺週不補入更早的零散資料夾。週六活動/封存資料夾 (例如 2026-07-11、2025-12-13、2025-06-14) 不進清單。

- 每個連結（錄音/講道投影片/報告投影片/逐字稿/教材/影片）只有發布檔案裡有值才畫，缺的不畫空連結；按下一律用 Chrome Custom Tab（`WebBrowser.openBrowserAsync`）開啟，不用 App 內建的 WebView。
- 以前的各週依日期新到舊排序 (2026-10-14 起；之前照 `past` 陣列順序)，不去重。
- 長的名稱、講員可以換行，不截斷；連結可隨手機寬度換行。
- 以目前台北日期判斷年份：今年顯示月/日（`9/20`），其他年份顯示年/月/日（`2025/12/13`）；離線時也相同。

### 報名人數與好友名單（後端，`server/eventRegistrations.ts`）

- 名單來源是教會自己的 Google 表單，透過 Apps Script 推送到 `/api/integrations/form-registrations`；推送只帶「姓名＋選的日期」，LINE ID、年齡等欄位從不進到這個系統。
- 推送的驗證方式二選一：一個由 session secret 派生的固定金鑰（`x-qingmu-registration-key`），或表單擁有者自己 Google 帳號簽的 identity token（`ScriptApp.getIdentityToken()`），且該 token 的 audience 第一次接受後就會被釘住，之後只認同一個 audience。
- 姓名比對：完全比對到唯一會員才算數；比對不到的名字（例如訪客、拼字不同）**只算進總人數，不會綁定到任何會員**，因此不會出現在任何人的好友名單裡。
- 每次推送都是「重寫」而非「疊加」：從昨天（Taipei）起的日期，先整批刪除舊的報名紀錄再寫入這次推送的內容，所以取消報名會反映成總數變少；昨天之前的舊日期不受影響。
- 一個會員讀某天的報名狀況時，只看到：總人數、自己是否報名、以及**自己朋友關係表裡有報名的人**的名字——不會看到不是朋友的其他報名者姓名。

### 青少｜主堂與週刊 (`app/(tabs)/announcements.tsx`、`src/ui/bulletin/`、`server/bulletins.ts`)

- 公告最上面「青少」「主堂」兩個分頁，預設打開自己的那一邊，還沒選或讀不到歸屬時是青少。青少分頁就是原本的公告。
- 主堂分頁只放週刊，不放公布欄的其他貼文。每週一段：「10/11 (日) 週刊」和「3 張・點圖片放大」，下面照貼出的順序排每一頁。點一頁開全螢幕：黑底，兩指放大 (最多 4 倍)、放大後一指移動，沒放大時左右滑換頁，右上角 × 回去；上方寫「10/11 週刊 2 / 3」，第一次放大或滑動前，下方提示「兩指放大縮小・左右滑換頁」。
- 每一頁都帶成員的登入 token 去要 (`authorization: Bearer …`)。圖片來源一律寫成陣列 `[{ uri, headers }]` (`bulletinPageSource`, `src/services/bulletinClient.ts`), 清單 (`BulletinBoard`) 和全螢幕 (`BulletinViewer`) 用同一個。原因：React Native 0.85 的 Android `Image` 只有 `source` 是陣列時才把 headers 交給原生元件，單一物件 `{ uri, headers }` 的 headers 被丟掉，後端回 401, 頁面一片白 (0.5.34 在 Pixel 發現，2026-10-19)。iOS 兩種寫法都會帶。
- 圖還沒到的頁 (2026-10-20)：每一頁先顯示跟那一頁同比例的灰框和「週刊載入中…」，圖到了才換成圖；載不到時灰框寫「這頁載不到，點一下再試」，點一下重新要這一頁 (不會打開全螢幕)。頁的無障礙標籤跟著狀態走：「8/30 (日) 週刊第 1 頁，載入中」→「…，點了放大」，或「…第 1 頁載不到，點一下再試」(`src/ui/bulletin/BulletinPageStatus.tsx`)。
- 清單用手機大小的圖 (2026-10-20)：清單向後端要 `?w=<寬度>` 的縮圖，寬度取 720、1080、1440 裡面蓋得住清單寬度的最小一個 (差 5% 以內算蓋得住，`src/domain/bulletinWidths.ts`)，例如 Pixel 8 和 iPhone 17 都是 1080。點開全螢幕才要原圖；原圖還沒到時先顯示清單已經有的那張縮圖，頁的標籤寫「8/30 週刊第 1 頁，載入中」，原圖到了變「8/30 週刊第 1 頁」；原圖載不到時頁面中間有「這頁載不到，點一下再試」按鈕。
- 全螢幕的狀態列 (2026-10-20)：狀態列那一塊維持 App 的淺色底，時間和電池照常看得到；黑色的看圖區和上方「8/30 週刊 1 / 2」那一列從狀態列下面開始。兩個平台同一種排法。
- 還沒有週刊時寫「還沒有週刊。公布欄貼出週刊後，會出現在這裡。」；讀不到時寫「暫時讀不到週刊。」和「重新讀取」按鈕。舊後端沒有這個 API，當作還沒有週刊。
- 週刊從哪裡來：教會在 LINE「竹科靈糧堂訊息公布欄」群組貼週刊，機器人「光佑_bot」在群組裡。只看這個群組的照片：bot 也在青少牧區公告群、青崇輔導/小組長群組，那些群組的照片不下載。同一個人貼的 A4 直式頁 (高寬比 1.36–1.47、寬至少 600 像素)，每張跟上一張相隔 10 分鐘內，兩張以上就是一期週刊；同一個人 3 小時內補貼的 A4 頁併進同一期。日期是第一頁貼出當天或之後的那個主日 (台北時間)；同一個主日之後又貼一整期，就換成新的。其他照片只看大小就丟掉，不存、記錄裡也沒有任何可以認出照片或人的資訊。
- 下載照片用頻道 ID 和頻道密鑰換來的 15 分鐘權杖 (`server/lineContent.ts`)，不存長期權杖；機器人只收不發話。
- 怎麼認公布欄群組 (`server/lineGroups.ts`)：某個群組第一次有事件時 (bot 被加進群組的 `join` 也算)，後端用同一個權杖向 LINE 查群組名稱 (群組資訊 API)。名稱開頭是「竹科靈糧堂訊息公布欄」的是公布欄群組，週刊和靈修 ([reader.md](reader.md)) 只從這個群組收；開頭是「青少牧區公告」「青崇輔導」的記成青少公告群和輔導群，目前只記下來，訊息不處理。群組編號和名稱存在私人部署的 `line-groups.json`，不存訊息和成員；之後只看群組編號，不再查名稱。記錄只寫一行 `LINE_GROUP_SEEN name=… purpose=…`，沒有訊息內容和使用者 ID。查不到名稱 (網路錯誤、私人檔案裡沒有頻道 ID) 時，那一則不當成公布欄群組，記 `LINE_GROUP_LOOKUP_FAILED`，下一則再查。

## 決定（為什麼這樣做）

**刻意不做：**

- **主堂分頁只放週刊原圖，不做文字版、也不放公布欄其他貼文** (維護者 2026-10-17)：週刊本來就是給成人看的一份完整公告，照原樣看最不會出錯；其他貼文 (活動照片、轉傳) 跟公告無關。保留 8 週。
- **認週刊的規則照公布欄的歷史定** (2026-10-17 回測 7/12–10/13 共 74 張)：13 期週刊都是同一個人在主日凌晨貼的 3 張 A4 (原圖 1722 × 2435)，同一期的頁在兩分鐘內貼完，只有 9/27 第 3 頁晚了 46 分鐘；其他照片是活動海報、早安圖、生活照、手機截圖，另有兩張別人單獨貼的 A4 大小傳單。歷史裡看不到 LINE「一次傳出」的標記，所以規則不靠它，改看同一個人、時間相近、兩張以上；晚貼的頁 3 小時內併入。單張的 A4 傳單不會被當成週刊。LINE 只保存幾週的原圖，更早的只剩縮圖，回測用縮圖量比例。
- **只收公布欄群組，別的群組只記名稱** (維護者 2026-10-20)：bot 要加進青少牧區公告群和青崇輔導/小組長群組，之後拿來跟「下次聚會」對答案；那些群組的照片絕不能進週刊，文字也不能存成靈修。群組用名稱開頭認一次，之後只看群組編號；查不到名稱時寧可漏收一則，不冒險收錯群組。

- **不做小組（RPG）、LINE 群組、通話等功能**：主導覽只留讀經和積分，這些入口已經被產品決定移除；現在看到的殘餘程式碼（`src/services/lineLinks.ts`、`app/(tabs)/groups.tsx`）只是為了讓已安裝的舊版 App 不會壞掉，不是還沒做完的功能。（來源：[../design/reading-gamification-v1.md](../design/reading-gamification-v1.md) §1.1 CL01）
- **報名比對只用姓名和日期，不收集 LINE ID、年齡等其他欄位**：這是隱私政策定下的界線，不是資料沒串接好。（來源：[../play/privacy-policy.md](../play/privacy-policy.md)「我們收集的資料」）

- **發布檔案採「多欄位、忽略未知鍵」的格式**：新版加欄位不會讓舊版 App 壞掉，新版讀到舊格式的檔案也有退回顯示——因為後端承諾舊版 App 仍要能正常連線。（來源：[../../AGENTS.md](../../AGENTS.md)「編輯注意」：後端要向下相容）
- **公告在 iOS 移植計畫裡被列為低風險、不特別客製化**：因為這是同一份 React Native 元件與同一個 HTTPS GET，兩平台沒有分支。（來源：[../superpowers/plans/2026-09-29-ios-parity.md](../superpowers/plans/2026-09-29-ios-parity.md) §3 第 9 項）
- **第二堂照規劃表顯示主題和負責人，Note 欄不顯示**：2026-10-01 曾決定第二堂一律只寫「青少團契」，理由是規劃列 (例如「創世記3~5章／分組進行」) 是同工安排用的。到了 10/25 的「吃喝玩樂躺平系列: 青年館電影院」，那條規則讓 App 只顯示「青少團契」，跟同工發給大家的內容對不上，所以改回照表格顯示。兩個第二堂分頁 (每月第一到第四週) 都一樣；舊版 App 讀的 `topic`/`owner` 照舊以第一堂為主。(維護者 2026-10-20 決定，取代 2026-10-01 的決定)
- **排程發布一律用 GitHub main 的程式，不用開發中的工作目錄**：`tools/announce/run.cmd` 先把 main 取到排程專用的 checkout 再執行；拿不到就不發布。2026-10-02 第二堂的修正已合併一天，但排程跑的是沒更新的工作目錄，09:00 又把第二堂蓋回團契規劃。（維護者 2026-10-02）
- **分類必須看內容，不能要求大家照格式命名**：2026-10-11 的讀書會投影片曾被檔名規則歸成第一堂報告。改用一次便宜 LLM 判斷堂次/角色；失敗保留原本發布能力。第一堂舊欄位不改意義，第二堂透過新增欄位提供。近期週聚會和零散活動/封存資料夾分開，避免後者混入歷史清單。 (維護者 2026-10-13 工單決定)
- **以前的主日固定日期在上、按鈕在下，非今年的日期顯示年份**：按鈕數量和手機寬度不改變行的結構，避免少量按鈕擠到日期右側或誤認年份。（維護者 2026-09-30 決定）
- **講道紀錄一個主日一張卡，最新的標「上週」**：取代「上次講道」加「以前的主日」兩段，每週長得一樣，往下滑就是更早的週。(維護者 2026-10-14；來源：[../superpowers/plans/2026-10-14-mock-1014-redesign.md](../superpowers/plans/2026-10-14-mock-1014-redesign.md))
- **下次聚會用深色日期塊；資料連結是文字加小圖示，不用按鈕；同類兩份檔案編號「報告投影片 1、2」，不印檔名；沒有內容的堂次收成一行；服事名單只顯示短的角色名**：一眼看到日期，卡片不被按鈕和長檔名塞滿。(維護者 2026-10-14)
- **週刊圖片來源寫成陣列，兩個平台同一種寫法，不加 `Platform.OS` 分支** (2026-10-19)：Android 只送陣列裡的 headers, iOS 兩種都送，陣列兩邊都對。守衛 `tests/ui/imageSourceHeaders.test.ts` 掃 `src/`, `app/`, 任何帶 `headers` 的 `{ uri, … }` 不在陣列裡就失敗；同一個測試也核對 React Native 原始碼 (`Image.android.js`, `ReactImageView.kt`) 還是這樣做，升級 React Native 時會知道。
- **後端的週刊 cookie `qm_bulletin` 保留** (`server/bulletinAccess.ts`, 另一個 PR 加的)：0.5.35 以前已經裝好的 Android App 還是用單一物件，要圖時不帶 token; cookie 讓它們不用更新也看得到週刊。新版 App 每一頁照樣帶 token, iOS 流程 `44-bulletin` 也只認帶 token 的請求，不靠 cookie.
- **iOS 流程不只看有沒有框**：Maestro 分不出圖有沒有真的載入 (空白的框和有圖的框一樣)，所以 `44-bulletin` 跑完，`scripts/ios/run-flows.sh` 讀 `scripts/ios/count-proxy.ts` 的請求紀錄 (`scripts/ios/check-bulletin-requests.ts`)：每一頁都要帶 bearer token 去要、而且回 200, 任何週刊請求回 401 就算失敗。count-proxy 只記有沒有帶 token, 不記 token 本身。Android 的雲端驗證沒有跑流程，Android 的寫法靠上面的 unit 守衛擋。2026-10-20 起流程還會等頁的標籤從「載入中」變成載好的樣子 (圖真的到了)，請求紀錄也要看到清單要的是縮圖、全螢幕要的是原圖，而且縮圖比原圖小 (count-proxy 多記 `bytes=` 回應大小)。
- **假資料週刊每次跑的時候畫出來，不放進 repo** (2026-10-20，取代 2026-10-19 的「兩張小的 A4 測試圖」)：縮圖要有東西可以縮，假資料要跟 10/18 週刊一樣是 2481 × 3509；這麼大的兩張圖放進公開 repo 是幾 MB 的二進位檔。`scripts/ios/make-bulletin-fixture.ts` 用固定的亂數畫標題列、兩欄像字的筆畫、表格和一塊照片，壓出來每頁約 1.2 MB，跟真的週刊差不多。不是真的週刊。
- **縮圖在後端做，做一次存起來** (2026-10-20)：10/18 的週刊每頁 2481 × 3509，手機清單只需要約 1080 寬，LTE 上清單白了 2–5 秒 (Pixel, 0.5.35)。後端 `server/bulletinsResize.ts` 照 `?w=` 縮成 720、1080 或 1440 寬，存在原圖旁邊 (`1.w1080.jpg`)，之後直接讀檔。只做這三種寬度，別的數字都歸到其中一個，不會一個數字一個檔。
  - 縮圖工具用 `jimp-compact` (純 JavaScript 的 Jimp 0.16)，不用 sharp：expo 本來就裝了它 (expo-asset、expo-notifications 經 `@expo/image-utils`)，後端套件資料夾不用多裝東西，也沒有原生程式。`package.json` 寫明這個依賴，裝出來的套件不變。
  - 解一張 A4 要約 1 秒，所以放在 worker thread 一次做一張，不卡住其他請求；做完 worker 就結束，沒有常駐程式。
  - 找不到縮圖工具、圖解不開、原圖本來就比縮圖窄，都直接給原圖：清單慢一點，但不會空白。縮圖做到一半週刊被換掉 (同一個主日重貼)，這張縮圖不留。
  - 舊版 App 不帶 `?w`，照舊拿原圖；新版 App 連到還沒更新的後端，後端不認 `?w`，也是拿原圖。
- **全螢幕的狀態列維持 App 的淺色底，不改成白字** (2026-10-20)：改狀態列顏色要動到 Modal 的視窗設定，Android 和 iOS 的做法不一樣，而且 App 其他畫面都是淺底深色圖示；讓黑色看圖區從狀態列下面開始，兩個平台同一份排版就好。iOS 流程跑完會截圖檢查：狀態列那一塊是淺色、黑色從它下面開始 (`scripts/ios/check-bulletin-viewer.ts`)。

**待確認（沒有記錄，請維護者確認是否刻意）：**

- 報名人數為 0 時，整段報名狀況完全不顯示（不是顯示「目前 0 人報名」）：目前找不到記錄這個決定的理由。

## 平台差異

- 公告本身沒有 Android/iOS 分支；程式碼是同一份 React Native 元件與同一個 HTTPS GET。
- 週刊圖片有一處 React Native 的平台行為差異：Android 的 `Image` 只從陣列 source 送出 headers, iOS 每一種 source 都送。App 一律用陣列，兩邊同一種寫法 (見「決定」)。
- iOS 的 iOS-parity 計畫（`docs/superpowers/plans/2026-09-29-ios-parity.md` 第 9 項）本身把公告列為「預期不用改」的低風險項目，只用 Maestro 截圖確認畫面能開。

## 資料與後端

- 公告內容本身**不經過** `server/`：直接讀 GitHub raw 上的 `announcements/latest.json`（本 repo 內 `announcements/latest.json` 就是目前發布的版本，範例欄位：`week`、`sermon`、`next`（含 `sessions`/`roles`）、`standing`、`past`）。
- 報名狀況才經過後端：`GET /api/me/groups`-同層的 `GET /api/me/event-registrations?date=YYYY-MM-DD`（`src/services/eventRegistrationClient.ts` 呼叫），需要 Bearer session token 與 `x-qingmu-member-id`。
- 後端資料表：`event_registrations`（誰報名哪天）、`event_registration_totals`（每天總人數）、`form_sync_audience`（釘住的推送者 Google audience），定義在 `server/eventRegistrations.ts` 的 `ensureEventRegistrationSchema`。
- 發布：維護者電腦上的排程執行 `tools/announce/run.cmd` → 把 GitHub main 取到排程專用的 checkout，用那份程式產生公告、交給 `tools/announce/publisher.ts` 從另一個專用的 main checkout 推上 `announcements/`。開發用的工作目錄在哪個分支、有沒有改到一半，都不影響發布；拿不到 main 的程式或任一步失敗就不發布，上週的檔案留著（舊但不錯），原因寫在 `tools/announce/last-run.log`。
- 週刊：`GET /api/bulletins` (最新主日在前，每頁的寬高)、`GET /api/bulletins/:主日/:頁` (原圖，只給已登入成員)、`GET /api/bulletins/:主日/:頁?w=720|1080|1440` (同一頁的手機縮圖，第一次要時做好、存在原圖旁邊，見「決定」)。檔案放私人部署的 `bulletins\<主日>\` (啟動程式帶 `QINGMU_BULLETIN_DIR`)，頻道 ID 放在 LINE 頻道密鑰同一個私人檔案。看過的 LINE 群組放同一層的 `line-groups.json` (啟動程式帶 `QINGMU_LINE_GROUPS_FILE`；沒帶時只記在記憶體，重開後每個群組再查一次名稱)。
- 週刊圖檔在 Android：React Native 的 Android Image 只有在 `source` 是陣列時才送出 headers，所以 App 要圖時沒帶登入 token，頁面一片白 (2026-10-19 在 Pixel 發現)。讀清單時後端多回一個 cookie `qm_bulletin` (`server/bulletinAccess.ts`)，只開週刊圖檔、7 天，每次讀清單都換新，每次要圖都再確認帳號還是啟用的。Android 的 fetch 和圖片載入共用同一個 cookie 儲存，所以已經裝好的 App 不用更新就看得到。
- 舊版 App 相容：發布檔案格式是「多欄位、忽略未知鍵」設計，新加欄位不會讓舊 App 壞掉；反過來新 App 讀到沒有 `sessions`/`roles`/`sermonSlides` 的舊檔案也有對應的退回顯示。
